## U1 生成器与判官提示词原文未公开 → 外人无法逐字重跑上游读数
- 现状：《初测 v1.0》§二 只描述了判官口径（三档、盲评、含断点前上下文、T=0、thinking off），提示词原文与生成器提示词在私有层。
- 影响：本站只能按公开口径重写（sha 写进 config.json），读数与上游 v1.0 **不可直接互比**。
- 建议：公开 C 型生成器与判官提示词原文（或其 sha＋全文），并在作答契约中引用。

## U2 作答契约未写明"闭卷／无记忆条件"下生成器能看到什么
- 现状：契约写"材料＝截至断点的 corpus（题卡给出材料终点与提问）"；初测闭卷臂 basis 为 0，但契约要求 basis ≥1 项。
- 本站做法：底子臂看到题面（题卡 `pre` 原文与行号），可从中逐字引用。
- 建议：契约补一节"无材料条件"：是否给 `pre`、basis 是否豁免。

## U3 有 11 组卡共用同一条答案键（同文件同答案行）
- 机械核对：`(file, answer.human.line)` 重复 11 组，例如 `确认协议内容.md` L1861／L12393／L38464／L39152／L39495／L40131，`信任协议权重调整.md` L51400，`学习能力理论讨论邀请.md` L17520，`接入共同信任协议.md` L315／L8601，`智能论恢复确认.md` L17688；其中 2 组为 3 卡共用。
- 影响：89 卡并非 89 道独立题，配对统计的有效样本量偏小、区间偏乐观。本站在报告中如实说明，不去重（不改题）。
- 建议：在题卡中加 `answer_group` 字段，或在筛选记录里给出"独立题数"。

## U4 C-116 脏卡（答案键是 API 响应 JSON 残片）仍在定稿 89 卡中
- 上游已在 caveats 记录、锚集排除；本站同样**如实计入**分数、锚集排除。
- 建议：v0.2 题卡剔除或标 `dirty: true`，便于各家统一处理。

## U5 跨文件泄题未处理
- 现状：防泄题口径只处理"同文件答案行之后"的材料；16 份会话之间有时间先后，后发生的会话可能复述前一会话断点后的内容。
- 建议：给 16 份语料补会话起止时间（或先后序），过滤"晚于断点的其它会话"。

## U6 若干口径未写到可复现粒度
- 行号：语料为 CRLF，题卡行号按 `\n` 切分（本站核对一致），建议在契约写明。
- "材料上限 12,000 字符/卡"在 k 条材料间如何分配、截断从哪端截，未写明（本站：按相关度顺序均分剩余额度、以最相关行为中心开窗、行对齐）。
- 12 条"无关负锚"的内容未公开（本站自备 12 条与语料无关的日常句子，作判官校准材料，不是考题）。
- BM25 参照臂的切块规则未公开（本站按轮边界聚块 ≥6,000 字符，得 1,595 块，与上游 1,611 块同量级）。

## U7 个别答案键是截断标题，信息量很低
- C-044 答案键为 `## 反思单元 · 复核确认 · 九问九答框架…`（语料该轮其实是长文档开头）；C-020/C-021 答案键同为"继续生成附录部分。"。
- 建议：筛选记录中对"答案键过短/仅标题"的卡做标注，供各家分层报告。
