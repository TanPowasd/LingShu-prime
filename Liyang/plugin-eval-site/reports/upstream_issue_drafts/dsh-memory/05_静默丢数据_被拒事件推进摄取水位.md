# [Bug/Data loss] 会话摄取时被密级拒绝的事件仍推进"已摄取水位"：换上正确令牌重试 `new_events=0`，这批对话永远不会再被导入，且无任何提示

> **是否已有人报**：未见同题（2026-10-10 查 issues 列表 81 条）。同类"静默"问题：[#56](https://github.com/FuRongJun-1999/dsh-memory/issues/56)（user/message 被 source.kind 过滤后完全静默）、[#52](https://github.com/FuRongJun-1999/dsh-memory/issues/52)、[#75](https://github.com/FuRongJun-1999/dsh-memory/issues/75)（对照 #38「缺件绝不静默」原则）；机制不同。

## 环境
见 `_公共环境.md`。

## 复现步骤
1. 签两个令牌：
   - R：`python3 -m md_cg.tokens issue --role recorder --actor r1`（非 designer 角色密级上限 internal）
   - P：`python3 -m md_cg.tokens issue --role designer --actor p1 --clearance private --ops-allow info,route,read,write,recent,goal,identity,whitebox,verify,ingest,session --layers-allow knowledge,contextual,structural,self,goals,unresolved,rejected`
2. 空库 B，用 R：`cg {"op":"ingest","action":"jsonl","path":"probe_session.jsonl"}`。
3. 同一库 B，换 P 重启服务，再调一次同样的 `cg(op=ingest)`。
4. 对照：空库 C 直接用 P 摄取同一文件。
5. （同样现象也可由 `mdcg_ingest` + README internal 令牌触发，库 E。）

## 期望
被拒的事件不算"已摄取"；换上有权限的令牌重试时这 50 轮能写进去。至少：返回体明确告诉调用方"有 N 条曾被拒、水位已越过、需要 reset 才能重导"，并给出 reset 方法。

## 实际
| 步骤 | 返回 | 录像 |
|:--|:--|:--|
| 2. 库 B + R | `new_events=50, written=0, denied=50`，hint"调用方需 MDCG_CLEARANCE=private 才能写入" | ⟦录像:dsh_install@00:15#53⟧ |
| 3. 库 B + P 重试 | `new_events=0, written=0, denied=0`，**hint=null，error=null** | ⟦录像:dsh_install@00:20#65⟧ |
| 4. 新库 C + P | `new_events=50, written=50, denied=0` | ⟦录像:dsh_install@00:17#59⟧ |
| 5. 库 E（mdcg_ingest 被拒后）+ P 重试 | `new_events=0, written=0, denied=0` | ⟦录像:dsh_install@00:21#68⟧ |

对照：在 ops 白名单层就被拒（`isError=true`，见草稿 04）的库 A，换 P 重试 **能** 50/50 写入 ⟦录像:dsh_install@00:18#62⟧——说明只有"进了写入层、逐条被拒"的事件才推进水位。

## 影响
用户第一次用错令牌（照 README／init 配置就会用错，见草稿 03、06）导入会话史 → 修好令牌再导 → 返回"0 条新事件"且无报错，看起来像"已经导过了"。这批对话**永久缺失**，除非用户知道去改水位。

## 建议
1. 水位只在事件 `written`（或明确终态如凭据禁表 REJECT 落 rejected 层）后推进；`denied` 的事件不推进。
2. 若保留现行为，返回体在 `new_events=0` 但该源存在历史 `denied>0` 时给 hint（含 `mdcg_watermarks` 的查看/重置用法），并在 README「写入凭据」节写明。
3. 回归测试：同一源先低权限摄取（全拒）再高权限摄取，必须 written=N。
