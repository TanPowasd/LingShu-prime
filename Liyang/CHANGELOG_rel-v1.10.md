# CHANGELOG rel-v1.10（zh-v13：中文可选语义通路 v11c 的冷查询延迟修复——rel-v1.6 未验收项）

相对上次推送版（Liyang/ = rel-v1.9，LingShu-prime 48d43aba / 发布树 rel-v1@3d9761b2）的增量升级：**只改中文带模型（bge-reranker-base + bge-small-zh）时首个触发稠密补入的查询时延，不改任何名次与分数**。
无模型路径、英文通路、版本链均未改，回归门逐题相同。

## 为什么要这一版
rel-v1.6 把 zh v11c（v7.1 + 稠密补入 sem_dense 20 / m 5 / cap 2 / τd 0）设为带模型缺省时，**查询延迟没有验收**。zh-v13 按 PREREG_ZH 修订 11.1 补测（DuRT dev 前 6 库 × 20 题 = 120 题，每库 260 段；臂间逐库 ABBA 轮换；冷 = 打分件/稠密件已载入、分数与向量缓存为空）：
v11c 冷 p95 **31.0 s** 对 v7.1 **18.6 s**（**1.67×**，超过预登记上限 1.5× 且绝对值远超 300 ms）；热 p95 27.0 对 28.8 ms（限内）。
原因：库里第一个触发稠密补入的查询要把**整库**段落现编 bge-small-zh 向量（260 段 ≈ 40 s，2 核且与他线共享），落在该查询的墙钟上。这是 v1.6–v1.9 的真实缺陷。

## 改了什么（纯时延件，名次逐位不变）
- **F1 `prefetch_dense()`**（`semrank.prefetch_dense` / `MemoryEngine.prefetch_dense` / 兼容门面 `SpacetimeMemoryEngine.prefetch_dense`（compat_engine.py））：批量写入后预先把全库可检索段落的稠密向量编进缓存。与首次触发补入时**同一 SQL、同一过滤、同一排序、同一批次** ⇒ 向量逐位相同、名次不变。无稠密件 / 无打分件 / sem_dense = 0 / 库超 sem_dense_max ⇒ 不做事、返回 0。
- **需要宿主调用**：本版**没有**把预取接进写入路径的缺省行为。理由：预取把约 38.7 s/库（260 段，本机负载下 ≈150 ms/段）的编码挪到写入期；若在写入结束时自动后台跑，会与宿主自身查询和测试/门脚本抢 2 核 CPU，并需跨线程共用 SQLite 连接，收益只在「新库首个触发补入的查询」——不值得在缺省路径冒险。宿主在批量导入/建库完成后调用一次 `engine.prefetch_dense()` 即可；不调用时行为与 v1.9 完全相同（首个触发查询照旧现编）。
- 随附 **C1 `sem_casc`**（截断后前 k 段由 bge-reranker-v2-m3 复打重排，PREREG_ZH 修订 11 C1）代码，**缺省 0 = 关，逐位不变**；结论见下。
- 测试：`tests_ng/test_semrank.py` 新增 prefetch 名次不变、sem_casc 缺省关与前 k 段内重排单测。

## 延迟验收（PREREG_ZH 修订 11.1 协议；上限：v11c 冷、热 p95 各 ≤ 1.5 × v7.1 同口径，或绝对 ≤ 300 ms）
读数 `bench_zh/runs/durt/v13/lat/{base,fix}/`：

| 次 | 臂 | 冷 p50 | 冷 p95 | 热 p50 | 热 p95 | 冷 p95 对 v7.1 |
|---|---|---|---|---|---|---|
| base（修复前） | v7.1 | 11.7 s | 18.6 s | 11.5 ms | 28.8 ms | 1× |
| base | v11c（v1.6–v1.9 缺省，不预取） | 14.3 s | 31.0 s | 10.2 ms | 27.0 ms | **1.67×** ✘ |
| fix（修复后） | v7.1 | 9.0 s | 15.1 s | 9.0 ms | 17.0 ms | 1× |
| fix | **v11c + prefetch_dense** | 10.8 s | **19.9 s** | 13.7 ms | 34.3 ms | **1.32×** ✔ |

- 热 p95 34.3 ms：对 v7.1 2.0×，但绝对 ≤ 300 ms ⇒ 按上限的「或」条款通过（热路径本版未改；base 次热比 0.94×，两次之差是负载噪声）。
- 预取耗时（写入期）≈ **38.7 s/库**；冷查询 p50/p95 仍是秒级，因为中文交叉编码器每题约 40 对 × ≈300 ms（v7.1 同样如此，这是 v7 起的既有成本，不是本版引入）。
- 照实：本机 2 核，与 gen/chain 线后台进程共享；绝对毫秒受负载影响，比值靠同次逐库轮换配对。冷遍名次：fix 次 v11c+prefetch 与 base 次 v11c **120/120 逐题相同**。

## C1 级联（sem_casc）结论
`sem_casc` 随附、**缺省 0（关）**，本版不据此改任何缺省。dev 评估（DuRT dev，k ≤ 3；判据：nDCG 有增益、误用不升、延迟在限内，才冻结并各跑一次 DuRT hold3 / T2R2 r2test）在本版推送后进行，结论写入 PREREG_ZH 修订 11a 与 REPORT_ZH §17，随下一版发布树附带。

## 没赢的地方（照实）
- 本版不含检索质量提升；中文冷查询仍是秒级（交叉编码器成本），只是去掉了首触发整库现编的额外几十秒。
- 预取不是缺省行为，宿主不调用就拿不到修复。
- 热 p95 对 v7.1 比值 2.0×（绝对值 34 ms 过限）。
- C2（BGE-M3 作补入生成器）因成本放弃、C3（零模型查询扩展）预检无效放弃，见 PREREG_ZH 修订 11a。
