## 先写未胜项与遗留项（照实）

对上游 cb3a6ea 的未胜项本版只收窄了「写入非线性」与「晋升延迟」两项，**都仍不如上游或仍随规模变慢**：

| 项 | 上游 cb3a6ea | rel-v1.25 | **rel-v1.26** | 说明 |
|---|---|---|---|---|
| 冷 import（`import lingshu_ng.compat`，无字节码缓存 / 有缓存，9 次中位） | 80.6 / 27.6 ms | 148.5–150.2 / 54.3–54.5 ms | **149.7–150.2 / 54.1–54.6 ms（未改善）** | 本轮剖析后**未改**，原因见下 |
| 晋升延迟（propose → verify → adjudicate，50 次均值，`tools/compare/vs_runtime.py` ng 侧） | 0.19–0.20 ms（rel-v1.21 记录） | 1k 4.44 / 4.48、10k 5.88 / 5.94 ms | **1k 3.76 / 3.95、10k 4.55 / 4.58 ms** | 中位 1k −13.6%、10k −22.8%，**未达 −30%**；仍约为上游 20 倍 |
| 写入非线性（100k 末 5 段每千条） | 10k 时每千条 23 → 451 s | 4.49 s | **3.57 s（0.795×）** | 仍随规模变慢：100k 首段约 1.6 s，末段约 3.6 s |

- **冷 import 未改的原因**（`_stab/r10/imp/`）：无缓存口径下约 100 ms 是 58 个模块的源码编译（`builtins.compile`），其余是文件打开与模块执行。`import lingshu_ng.compat` 载入的模块里，真正能推迟到首次使用的（`causal`、`graphquery`、`exchange`、`densefuse` 等）编译合计约 10 ms；
  `SpacetimeMemoryEngine` 的 6 个混入基类（`compat_world_sim` / `compat_world` / `compat_body` / `compat_frame` / `compat_providers` / `compat_stubs`）与引擎构造时就实例化的 `SelfStore / Maintenance / SkillBook / NegativeMemory / Insights / LongTermGate` 无法延迟而不改类结构或构造时机。估计可得约 7%，到不了 −20%，且推迟到构造期只是挪时间（「import + 构造 + 写一条」两版各约 156 ms），本版不做。
- **晋升延迟**：主要花在节点改标签后的整节点倒排重排（nkey 改为最大值 + 1，与 v4 删旧插新逐值相同的约定）——每次 propose / adjudicate 都把该节点所有词元的倒排条目移到末尾。本版把块内删除改成按位置切字节、前一块批量读，余下的是 SQL 改写本身；要再降需要合并「删 + 追加」为一次块改写，本版未做。
- 10k 写入持平（0.996–1.000×）：10k 时近重复候选占写入耗时的比例小，本版的改动在 10k 看不出来。1k 持平（0.997×）。
- 常驻内存、库体积不变（1.000×）；库体积仍大于上游。
- Windows 真机未测；MCP 适配器未与具体客户端实机联调；`hive_liyang` 名次表尾部跨次运行不确定（同 rel-v1.25）。

## 改了什么

1. **近重复候选降常数（写入路径）**：`lingshu_ng/store/neardup.py`（新，`TextIndex.near_duplicate_candidates` 的主体移入）。算法与判定同 rel-v1.25（前缀 + 逐步校验 + 剪枝），只改实现：
   - 前缀倒排的长度过滤：v1.25 逐条 Python 循环；本版按 |B| < 256 时把 grams 数组的低 / 高字节各查一次 256 项表再按位与（`bytes.translate` + 大整数与），否则查 65536 项表；`itertools.compress` 选行、`Counter.update` 计数。
   - 每个候选的下限 need_B 只依赖 |B|，按 |B| 算一次（同一表达式）。首个校验步就会剔除的候选不再进入后续结构。
   - 剪枝「已命中 + 剩余可命中 < need_B」：v1.25 每步扫全部存活候选，本版按缺口分桶，剩余数每步减一时只弹出越界的那一桶。「读整条倒排 / 点查」的分支条件不变，读整条倒排求交改为集合交。
   - `postings.read_arrays`：一个词元的各块都是窄编码时拼接字节一次解码（`postings.read` 改为它的列表版，内容不变）；`TextIndex.postings_arrays` 供上面使用。
   剖析（`_stab/r10/prof/`，95k 基库续写 3000 条，cProfile + 逐语句计时）：v1.25 时近重复候选约占写入耗时一半，其中前缀倒排逐条过滤 / 计数与每步全量剪枝是主体；同段（单次）13.42 → 10.71 s。
2. **倒排块删除（晋升 / 改标签 / 删除路径）**：`postings.remove` 对窄编码块按键位置（二分）直接切字节，宽编码块照旧解码重编；「改后不足 BLOCK/4 的块并入前一块」所需的前一块改为一条语句批量读出——读的都是本次改写之前的库状态（与 v1.25 逐块查询读到的相同），合并判定、写出的行与返回的条数同 v1.25。
3. **等价性测试**（`tests_ng/test_neardup_r10.py`，新 14 条）：近重复候选在 6 组阈值 / 长短文本混合语料上对 rel-v1.25 原实现（`tests_ng/ndc_ref_v125.py`，原样拷贝）与全层暴力比对逐值相同（含 |B| ≥ 256 的查表退路）；字节查表与逐条查表逐位相同；`read_arrays` 与逐块解码相同（含宽编码块）；
   `remove` 在 6 组随机倒排（随机块长 5–128、宽编码、批量删除）上对 rel-v1.25 原实现（`tests_ng/postings_ref_v125.py`）连续 25 轮删除后块逐字节相同、返回条数相同。
4. **规模核对**（`_stab/r10/`）：95k 基库续写 2498 次，每次近重复候选新实现 = v1.25 实现（0 差，`prof/eq_ndc.txt`）；冻结墙钟写 10k / 100k 条，两版库内容规范化后（节点 id 换写入序号）`nodes`、`node_index`、`term_blocks`、`term_df`、`feature_df`、`edges`、`index_state` 的哈希**全部相同**（`t/weq_{10000,100000}_{A,B}.json`；100k 去重合并 428 次、新建 99572 条，两版相同）。
5. 文档：PERF_ng 本版读数；VS_UPSTREAM 未胜项表加 rel-v1.26 列；STABILITY 版本号与矩阵；API 快照版本 1.26.0（公开名字与签名无变化）。
