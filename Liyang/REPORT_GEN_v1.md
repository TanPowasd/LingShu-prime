## 做了什么（全部在 ng 公开 API 内，可配置）

新模块 `lingshu_ng/lexical.py` + `retrieval.py` 的 Q10 路由：

1. **按语言路由**：查询里中日韩字符占（中日韩 + 其他字母）的比例 < `route_cjk`（0.3）且有可用词元 → 走词级通路；否则走原通路（Q1–Q9 代码一行未动，中文结果逐位不变）。
2. **分词（L1）**：NFKC + casefold；拉丁/数字串按词切，去英文停用词，轻量词干（所有格、复数、-ing/-ed、-ation/-ness、-ly、尾 e）；中日韩串取字二元组。
3. **索引（L2）**：拉丁词干以 `\x1e`+词干写进同一张派生倒排（`store.textindex.terms_of`，写时维护、df 精确）。词元格式版本 `index_state('lexv')`；旧库打开时整体记脏，首读前批量重建（`TextIndex.ensure_lexical`）。T1「派生表 = 全量重算」不变。
4. **打分（L3）**：BM25（k1=1.2，**b=0.5**；dl/avgdl 用正文字符数，avgdl 读库统计并缓存）+ SDM 邻近（有序紧邻 + 无序窗口 8，权重 0.85/0.10/0.05）+ **写入序上下文聚合**（s'(n) = s(n) + β·max_{0<d≤span} decay^(d−1)·s(邻居)，**β=0.8、span=3、decay=0.6**）。相关度 = 分 / 池内最高分，与原相关度同量纲，Q4 组合分（重要度/置信度/近因）权重不变；词级通路不再做二元组 idf 重排（R1），R2 长块多样化保留。
5. **候选（L4）**：查询词元按 df 升序展开倒排（行数预算 200000），按命中词元 idf 和取前 3000 名精排；不超预算/上限时与暴力全库精排（`brute_force`，已同步支持词级通路）逐名次相同（有测试）。
6. **配置 API**：`LexicalConfig`；`MemoryEngine(lexical=...)`、`MemoryEngine.set_lexical(cfg|dict|**kw)`、`MemoryEngine.lexical`；兼容层 `SpacetimeMemoryEngine.set_lexical_config`；环境变量 `LINGSHU_NG_LEXICAL`（JSON 覆盖）；`enabled=False` 完全回到旧通路。另有默认关的选项：段落项 `passage/gamma`、上下文补位 `ctx_fill`、方向系数 `ctx_prev/ctx_next`、伪相关反馈 `prf_*`。

默认值来源：b 与 ctx_* 由 dev 扫参选定（下节），其余取文献常用值。

## v2：库感知混合路由 `route_corpus`（PREREG 修订 4；冻结 9ffe1e9）

**动机（dev，修订 2·C）**：v1 按查询自身的中日韩字符占比路由（`route_cjk=0.3`）。中文用户常写「我 graduate with 什么 degree？」这类中文句式夹英文词的问句，占比 ≥ .3 时被送回中文二元组通路，在英文库上断崖（LME dev 该区间 .69 vs 强制词级 1.00）。

**设计**：查询同时含中日韩与非数字拉丁词元、且占比 ≥ .3 时，看**库**的中日韩词元份额（派生倒排 term_df 两段区间求和，按库缓存）：≤ θ 且查询至少一个拉丁词元在库中出现 ⇒ 仍走词级通路。中文库份额 .95–1.0、英文库 ≤ .02，两极分化，θ∈{.1,.5,.9} 在 dev 上读数完全相同，取中点 .5。纯英文、纯中文、纯数字查询不触及这条逻辑（惰性：不 flush、不读库）。

**轻度泄露（如实说明）**：v2 的第一个候选 `route_absent`（看查询中文词元在库内的出现率）被**状态链回归门否决**（现值 gold6 .667→.310：模板化中文问句在中文库里出现率只有 .29–.57，且数字被当作拉丁词元），之后才改成 `route_corpus`。状态链门的语料含 test 文档，所以门的失败信号参与了设计选择，属于轻度泄露。它只涉及「中文库上不能误路由」这一侧（v2 在中文库上与 v1 逐位相同，见下），不涉及任何英文 / 混合 test 读数；混合 test 问句在 v2 冻结之后才生成。

**o030i「bug」的定位（不是路由 bug）**：之前看到 route_corpus 打开后 HMB 查询 o030i 的 top-10 变了，但 `_route` 对它返回 False。定位结果：
- 组合召回 `recall` 的 recency 项读墙钟（`0.15·1/(1+Δt/86400)`，分数舍入到 6 位），每秒约 1.7e-6 的漂移足以在舍入边界上翻转同分次序；节点 id 由 `os.urandom` 生成，同分时按 id 定序。所以**同一份代码重跑也会换序**：05003d3 自己在进程内先后建两个库对比，184 问里有 34–62 问的 top-10（名次或 6 位分数）不同（两次试验）。原 /tmp/dbg.py 还在同一引擎上交替跑 off/on，recall 的 touch 会改 last_access，比较本身就有偏（重写为 `bench_gen/dbg/route_repro.py`）。

- test 集不是全新的：ng@875d838 与 TriCue 各臂在这 387/1149 题上的逐题读数之前已存在（prime-test item4，只看过总体均值）。gen-v1 的任何参数都没有在 test 上调过；v1 test 只跑了一次，另跑了一次预注册的消融臂。
