## 改了什么

1. **晋升路径的倒排改写合并（`lingshu_ng/store/blockmove.py`，新）**：节点改标签 / 改层后，`TextIndex._move_row` 把该节点移到新 nkey（「删旧插新」的 v4 约定，不变），倒排要做「旧键退出全部旧词元 + 新键进入全部新词元」。
   rel-v1.26 依次调用 `postings.remove`（一条定位语句 + 前一块批量读 + 删 / 写）与 `postings.add`（一条末块语句 + 改写），每个词元的块读写两遍。
   本版 `blockmove.move` 一次读出所涉的块，在内存里**按 `remove` 再 `add` 的同一规则**（块内按位置删、删空删行、不足 BLOCK/4 并入前一块、末块未满追加 / 已满开新块）模拟，只写出内容真正变了的块：
   - 读法：`term_df ≤ 4 × BLOCK` 的词元整条读块（一条语句；块集是所需块的超集，模拟结果相同），更长的词元只定位「含旧键的块、其前一块、末块」三块。df 只决定读法，不影响结果。
   - 同键改写（终裁去 `promotion_pending` 标签时，节点已是最大 nkey，`_move_row` 分配回同一个键）：绝大多数词元的末块「删掉末键再追加回同值」字节不变，直接跳过不写（判定条件与 `remove` 的删空 / 并块规则一一对应，见 `_same_tail`）。
   - 遇到宽编码块、键超 uint32、grams 超 uint16 或追加键不大于末键（不应发生）时返回 False、一行未写，调用方照旧走 `remove` + `add`。`TextIndex.FAST_MOVE = False` 可整体关闭（等价核对用）。
2. **倒排块写语句**：`postings._PUT` 由 `INSERT OR REPLACE` 改为 `INSERT … ON CONFLICT(term, bno) DO UPDATE`（`term_blocks` 无触发器、无二级索引，两者终值相同；后者免去冲突时的删后重插，90 行改写实测 0.30 → 0.15 ms）。
3. **缓存上限可配**（缺省不变）：`LINGSHU_NG_TOKEN_CACHE`（分词缓存，缺省 16384）、`LINGSHU_NG_BIGRAM_CACHE`（二元组集缓存，缺省 1024）、`LINGSHU_NG_NORM_CACHE`（规范化缓存，缺省 2048）；非负整数，0 = 不缓存，非法值退缺省并打一条 WARNING（`lingshu_ng.diag.cache_cap`，非公开 API）。只影响内存与速度，不影响任何读数。
4. **等价性测试**：`tests_ng/test_postings_move.py`（新 16 条）——小块（BLOCK=12、长倒排阈值 20）随机历史 12 组 × 400 步（新增 / 删除造碎块 / 同键与换键改写、grams 七成不变），每次 `move` 后 `term_blocks` **原始行**（块切分、bno、字节）与「`remove` 后 `add`」逐行相同；宽编码与超范围键拒绝且不写；引擎级随机改写序列 FAST_MOVE 开 / 关两库派生表原始行全等。
   对 `_same_tail` 的三处判定与追加分支做过变异检验（改坏任一处，16 条中 4–15 条失败）。`tests_ng/test_cache_cap.py`（新 2 条）。
5. **晋升随库规模增长的开销（`lingshu_ng/store/blockmove.py` 的 `move` 重写，r11 版保留为 `_move_r11` 作对照）**。剖析（`_stab/r12/prof/`：同口径建库快照 → 50 次 propose / verify / adjudicate；cProfile、SQL 计数与 EXPLAIN QUERY PLAN、按阶段计时）：
   - 1k 与 10k 每次晋升执行的语句条数几乎相同（50 次共 10684 / 10709 条），查询计划都是主键 / 索引查找，**没有随规模增长的全表扫描或全表计数**；派生索引重建里 move 以外的部分（df 计数、触发器队列、nkey 分配）1k / 10k 为 0.53 / 0.55 ms，重建以外（读节点、提案表、负记忆、标签 / 层改写）0.54 / 0.69 ms——后者 10k 多约 0.15 ms，逐语句看是同一批主键查找在更大的表上略慢，未再拆。
   - 增长全部在 `blockmove.move`（每次晋升两次：propose 加标签时节点换到新 nkey、终裁去标签时同键改写）：r11 读法对 `df ≤ 512` 的词元整条读块、更长的词元用三块定位语句，并把末块字节读回 Python 改写后整块写回。10k 时长倒排词元从 0 增到每节点约 21 个、每次换键读回 / 写回的块字节从约 17 KB 增到约 41 KB；
     分阶段（ms / 次晋升，1k → 10k）：换键 0.89 → 1.43、同键 0.46 → 0.69，其中「长倒排三块定位」0.00 → 0.44、「短倒排整条读」0.46 → 0.68。
   - 改法（结果与 `remove` 后接 `add` 逐行相同，见测试）：
     ① 同键改写先用一条语句取各词元**末块摘要**（n、是否窄编码、末键、末 grams、前一块 n，不读块字节），满足 r11 `_same_tail` 同一判定（块不变）的词元两侧都跳过；
     ② 删除侧一条语句只取「含旧键的块」与其前一块（前一块字节只在可能并块时取），按 `postings.remove` 的规则改写；
     ③ 追加侧一条语句在库内拼接末块（同 `postings._add_one` 的写法，末块有空位而为宽编码时不写、由受影响行数发现后对这些词元调用 `postings.add`，与原路径同样解码重编）。前提同 `postings.add`（新键大于这些词元现存全部键，textindex 换键取其余行最大 nkey + 1）。
   - `TextIndex._move_row` 取「其余行最大 nkey」改为两段主键范围查找（原 `WHERE nkey <> ? ORDER BY nkey DESC LIMIT 1` 的计划是倒序 SCAN，虽然只读 1–2 行）。
   - `NegativeMemory.check(kind, text, fuzzy=False)`（晋升提案时查否决负记忆）：给定 `kind` 时先按 `path_key` 走既有索引 `idx_rejected_key` 取精确同键行（原先每次读出全部开放负记忆在 Python 里筛）；有精确命中或 `fuzzy=False` 时结果与原筛选逐条相同（同序、同字段），否则照旧全表做模糊匹配。负记忆条数多时提案不再随之线性变慢（vs_runtime 基准里负记忆为空，读数里看不出这一项）。
   - **不改库结构**（`SCHEMA_VERSION` 仍为 6，未加索引），不改公开 API。
6. **测试**：`tests_ng/test_promotion_plan.py`（新 1 条，守卫）——晋升路径（300 条库上 24 次 propose / verify / adjudicate，含否决、否决后重提被拒、带密钥越过重提）执行的每条语句做 EXPLAIN QUERY PLAN，**不得出现对数据表的 SCAN**（允许虚表 json_each、常量行 / CTE、三张每次 flush 清空的写入期队列表 index_dirty / index_tomb / index_old；触发器体内语句不在 EQP 中展开、不在本测范围）。在 r11 代码上此测失败（`SELECT * FROM rejected_paths WHERE status='open'` 与 `node_index` 倒序 SCAN）。
   `tests_ng/test_postings_move.py`：原「宽编码拒绝」改为「宽编码块上删除与追加与原路径逐行相同」+「键 ≥ 2^32 / grams ≥ 2^16 拒绝且不写」；新增随机历史 8 组 × 400 步，混入宽编码块（8% 节点 grams = 70000）与「最大节点换到更小的新键」（其余行最大 + 1 < 旧键），每次 move 后原始行与 remove→add 逐行相同（共 +10 条）。
